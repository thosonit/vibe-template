# Next.js Architecture

Generic target architecture for a Next.js app starting from a fresh
`create-next-app` scaffold — this document defines the structure to grow
into as features land, not a description of what exists today.

## Principles

- Feature-first organization, not layer-first (no top-level `components/`,
  `hooks/`, `services/` dumping grounds for feature code — those are
  reserved for genuinely shared, cross-feature code).
- App Router, Server Components by default. A component is only marked
  `"use client"` when it needs interactivity, browser APIs, or state —
  never by default.
- Each feature owns its UI, server actions/route handlers, and data
  access. Shared code lives in `src/lib/` and `src/components/ui/`.
- No client-side data-fetching library (TanStack Query/SWR) — Server
  Components fetch data directly; client components receive data via
  props or call Server Actions. Introduce a fetching library only if a
  screen later needs client-side polling/optimistic UI that Server
  Actions can't cover cleanly (YAGNI).
- Prisma is the only data access layer — no raw SQL client, no second ORM.
- Immutable data objects; no in-place mutation (see project `CLAUDE.md`).

```text

├── app/
│   ├── layout.tsx                  # Root layout (html/body, providers, fonts)
│   ├── page.tsx                    # Root route "/"
│   ├── globals.css                 # Tailwind directives + CSS variables
│   ├── (marketing)/                # Route group — no URL segment added
│   │   └── about/page.tsx
│   ├── (app)/                      # Route group for authenticated app shell
│   │   ├── layout.tsx               # Shell layout (nav, sidebar) for this group
│   │   └── dashboard/page.tsx
│   ├── api/
│   │   └── <feature>/route.ts      # Route Handlers — only for webhooks/external
│   │                                # consumers; internal mutations use Server
│   │                                # Actions instead (see Data Mutations below)
│   └── <route-segment>/
│       ├── page.tsx                 # Page (Server Component by default)
│       ├── layout.tsx                # Optional nested layout
│       ├── loading.tsx                # Suspense fallback for this segment
│       ├── error.tsx                   # Error boundary (must be "use client")
│       └── not-found.tsx                # 404 for this segment
├── components/
│   └── ui/                         # shadcn/ui primitives (button, dialog, input...)
│       ├── button.tsx                # Generated by `shadcn add`, then customized
│       └── ...
├── features/
│   ├── shared/                     # Cross-feature code reused by 2+ features
│   │   ├── components/               # Shared feature widgets (e.g. user-avatar.tsx)
│   │   ├── actions/                    # Shared Server Actions
│   │   ├── queries/                     # Shared Prisma read queries
│   │   └── types.ts                      # Shared feature-level types
│   └── <feature-name>/
│       ├── components/               # Feature-local Server/Client components
│       │   ├── <feature>-list.tsx      # Server Component — fetches + renders
│       │   └── <feature>-form.tsx        # Client Component — interactive form
│       ├── actions/                   # Server Actions ("use server") — mutations
│       │   └── create-<feature>.ts
│       ├── queries/                    # Server-only data reads (Prisma calls)
│       │   └── get-<feature>-list.ts
│       ├── schemas/                    # Zod schemas — input validation, shared
│       │   └── <feature>-schema.ts     # by Server Actions and forms
│       └── types.ts                    # Feature-local types (DB row → view model)
├── lib/
│   ├── config/
│   │   └── env.ts                    # Typed, validated env accessor (see Configuration)
│   ├── db/
│   │   └── prisma.ts                   # Prisma Client singleton
│   ├── auth/
│   │   └── session.ts                   # Session read/verify helper (server-only)
│   ├── errors/
│   │   ├── app-error.ts                  # Base `AppError` class + subclasses
│   │   └── format-error.ts                 # Maps errors → user-facing message
│   └── utils/
│       ├── cn.ts                       # `clsx` + `tailwind-merge` class combiner

│       └── validators.ts                   # Shared, non-Zod validation helpers
├── hooks/                          # Shared client-only hooks (cross-feature)

└── middleware.ts                   # Auth/route guarding, runs before matched routes
```

```text
prisma/
├── schema.prisma                  # Data model, single source of truth
├── migrations/                     # Generated migration history (committed)
└── seed.ts                          # Dev/test seed script
```

```text
tests/
└── features/
    └── <feature-name>/
        ├── actions/                  # Server Action unit tests (mock Prisma)
        ├── queries/                   # Query unit tests (mock Prisma)
        └── components/                  # Component tests (React Testing Library)
```

`app/` holds routing only — a `page.tsx` should stay thin: fetch via a
`features/<feature>/queries/` function, then render a
`features/<feature>/components/` component. Business/query logic never
lives directly inside `page.tsx`.

`components/ui/` is exclusively shadcn/ui-generated primitives (or
near-identical hand-built ones following the same API shape) — generic,
app-agnostic, no business logic, no data fetching. Feature-specific
composition lives in `features/<feature>/components/`.

`features/shared/` is for code reused by two or more features but tied to
app/business concepts (e.g. user session, account state) — not generic
enough for `lib/`. If something is only used by one feature, it stays
inside that feature; promote it to `shared/` only once a second feature
actually needs it (YAGNI).

`schemas/` (Zod) is the single source of truth for a feature's input
shape — the same schema validates a Server Action's input server-side
*and* drives a `react-hook-form` resolver client-side, so validation
rules are never duplicated between client and server.

## Layering: Server-first + Server Actions

- **Page** (`app/**/page.tsx`): a Server Component (`async function`).
  Calls a `queries/` function to fetch data, passes the result as props
  to a `features/<feature>/components/` component. No Prisma calls
  inline in `page.tsx` — always go through `queries/`.
- **Server Component** (`features/<feature>/components/*.tsx`, no
  `"use client"` directive): renders data, can itself call `queries/`
  directly when it's a nested/streamed section (e.g. inside
  `<Suspense>`). Cannot use hooks, state, or event handlers.
- **Client Component** (`features/<feature>/components/*.tsx`, top of
  file has `"use client"`): owns local interactive state (`useState`,
  form state), calls a Server Action on submit, handles pending/error UI
  via `useActionState`/`useTransition`. Never calls Prisma or reads env
  secrets directly — only through a Server Action.
- **Server Action** (`features/<feature>/actions/*.ts`, top of file has
  `"use server"`): the only way client components mutate data. Validates
  input with the feature's Zod `schemas/`, calls Prisma (directly or via
  a `queries/` write helper), calls `revalidatePath`/`revalidateTag` to
  refresh affected Server Components, returns a typed result
  (`{ success: true, data } | { success: false, error }`) — never throws
  raw Prisma errors across the server/client boundary.
- **Query** (`features/<feature>/queries/*.ts`, server-only — mark the
  module boundary with `import 'server-only'` at the top): thin
  functions wrapping Prisma reads, return typed data shaped for the
  view. This is the only place `prisma.<model>.findMany/findUnique` etc.
  are called for that feature's reads.
- Dependency direction is one-way: `app/` → `features/<feature>/components`
  → `features/<feature>/{actions,queries}` → `lib/db/prisma`. Client
  Components never import `queries/` or Prisma directly — only `actions/`.
- Route Handlers (`app/api/**/route.ts`) are reserved for cases Server
  Actions can't cover: webhooks from external services, endpoints
  consumed by non-browser clients, or responses that aren't HTML/RSC
  (file downloads, streaming to a third party).

### Error handling in Server Actions and Client Components

Server Actions return a discriminated union, never throw across the
server/client boundary for expected failures (validation errors, not-found,
conflict). Only truly unexpected errors are allowed to throw and be
caught by the nearest `error.tsx` boundary.

```ts
// features/todos/schemas/todo-schema.ts
import { z } from 'zod'

export const createTodoSchema = z.object({
  title: z.string().min(1).max(200),
})

export type CreateTodoInput = z.infer<typeof createTodoSchema>
```

```ts
// features/todos/actions/create-todo.ts
'use server'

import { revalidatePath } from 'next/cache'
import { prisma } from '@/lib/db/prisma'
import { createTodoSchema } from '../schemas/todo-schema'

type ActionResult<T> =
  | { success: true; data: T }
  | { success: false; error: string }

export async function createTodo(
  input: unknown,
): Promise<ActionResult<{ id: string }>> {
  const parsed = createTodoSchema.safeParse(input)
  if (!parsed.success) {
    return { success: false, error: parsed.error.issues[0].message }
  }

  const todo = await prisma.todo.create({ data: parsed.data })
  revalidatePath('/dashboard')
  return { success: true, data: { id: todo.id } }
}
```

```tsx
// features/todos/components/todo-form.tsx
'use client'

import { useTransition } from 'react'
import { createTodo } from '../actions/create-todo'

export function TodoForm() {
  const [isPending, startTransition] = useTransition()

  function handleSubmit(formData: FormData) {
    startTransition(async () => {
      const result = await createTodo({ title: formData.get('title') })
      if (!result.success) {
        // surface result.error via toast/inline message — never a raw exception
      }
    })
  }

  return <form action={handleSubmit}>{/* ... */}</form>
}
```

Unexpected errors (network failure mid-request, Prisma connection error)
propagate to the segment's `error.tsx`, which must be a Client Component
(`"use client"`) receiving `{ error, reset }` props.

## Data Fetching (Server Components)

- Fetch data directly in `page.tsx`/Server Components via `queries/`
  functions — no client-side fetching library by default.
- Parallelize independent fetches with `Promise.all`, not sequential
  `await` calls, to avoid request waterfalls:
  ```ts
  const [user, posts] = await Promise.all([
    getUser(userId),
    getPostsByUser(userId),
  ])
  ```
- Use `<Suspense>` + a nested async Server Component to stream slow,
  independent sections instead of blocking the whole page on the
  slowest fetch.
- Revalidation: mutations call `revalidatePath(path)` (or
  `revalidateTag(tag)` for `fetch`-based external calls) from the Server
  Action — never rely on the client refetching manually.
- If a screen later needs client-side polling, optimistic updates beyond
  what `useOptimistic` + Server Actions provide, or cross-tab cache
  sharing, introduce TanStack Query for that feature only — don't adopt
  it app-wide preemptively.

## Data Layer (Prisma)

- `prisma/schema.prisma` is the single source of truth for the data
  model. Run `prisma migrate dev` to generate a migration on every
  schema change — never hand-edit generated SQL in `migrations/`.
- `lib/db/prisma.ts` exports a single lazily-instantiated `PrismaClient`,
  guarded against multiple instances in Next.js dev hot-reload:
  ```ts
  // lib/db/prisma.ts
  import { PrismaClient } from '@prisma/client'

  const globalForPrisma = globalThis as unknown as { prisma?: PrismaClient }

  export const prisma = globalForPrisma.prisma ?? new PrismaClient()

  if (process.env.NODE_ENV !== 'production') {
    globalForPrisma.prisma = prisma
  }
  ```
- Every feature's `queries/` and `actions/` import this shared `prisma`
  instance — never `new PrismaClient()` elsewhere.
- `queries/*.ts` files start with `import 'server-only'` so an accidental
  client-side import fails at build time rather than leaking a DB
  connection into the browser bundle.
- Prisma `select`/`include` shape query results directly into the view
  model the component needs — avoid over-fetching whole rows when only
  a few fields are rendered.

## Configuration (env)

- `.env.local` (gitignored, developer machine), `.env.development`,
  `.env.production` for environment defaults committed to the repo
  (no secrets in these — only non-sensitive defaults); actual secrets
  are injected by the hosting platform (e.g. Vercel project env vars),
  never committed.
- Commit a `.env.example` with placeholder keys documenting every
  required variable.
- `lib/config/env.ts` validates `process.env` once at module load with
  Zod and exports a typed, frozen object — no raw `process.env.X` access
  outside this file:
  ```ts
  // lib/config/env.ts
  import { z } from 'zod'

  const envSchema = z.object({
    DATABASE_URL: z.string().url(),
    NEXT_PUBLIC_APP_URL: z.string().url(),
  })

  export const env = envSchema.parse({
    DATABASE_URL: process.env.DATABASE_URL,
    NEXT_PUBLIC_APP_URL: process.env.NEXT_PUBLIC_APP_URL,
  })
  ```
- Only variables prefixed `NEXT_PUBLIC_` are exposed to the browser
  bundle — never prefix a secret with `NEXT_PUBLIC_`, and never import
  `lib/config/env.ts` from a Client Component if it validates
  server-only secrets (split into `env.server.ts` / `env.client.ts` if a
  project needs both).

## Auth & Middleware

- `middleware.ts` at the project root handles route protection
  (redirect unauthenticated users) and runs on the Edge runtime — keep
  it fast; no Prisma calls there (Prisma requires the Node.js runtime).
- `lib/auth/session.ts` exposes a server-only `getSession()`/`requireUser()`
  helper, called from Server Components/Server Actions that need the
  current user — never re-implement session parsing per feature.
- Route groups separate auth surfaces: `(marketing)` for public pages,
  `(app)` for the authenticated shell, each with its own `layout.tsx`.

## Styling (Tailwind + shadcn/ui)

- Design tokens (colors, radii, fonts) are defined once as CSS variables
  in `app/globals.css` and mapped in `tailwind.config.ts` — components
  reference Tailwind utility classes/theme tokens, never hardcoded hex
  values or magic spacing numbers.
- `components/ui/` primitives are added via the shadcn CLI
  (`npx shadcn add button`) and customized in place — don't hand-roll a
  duplicate of a primitive shadcn already provides.
- `lib/utils/cn.ts` (the `cn()` helper combining `clsx` +
  `tailwind-merge`) is used for all conditional/merged class strings —
  never string-concatenate Tailwind classes.
- Follow the anti-template design-quality rules from the global web
  rules (`~/.claude/rules/web/design-quality.md`) — intentional
  hierarchy, spacing rhythm, and designed hover/focus states, not
  default shadcn styling left unmodified.

## Naming

- Files/folders under `app/`: Next.js reserved names as-is
  (`page.tsx`, `layout.tsx`, `loading.tsx`, `error.tsx`, `route.ts`);
  route segment folders: `kebab-case`.
- Files elsewhere: `kebab-case.ts`/`kebab-case.tsx`.
- Components: `PascalCase` export, e.g. `export function TodoForm()`, in
  a `kebab-case.tsx` file (`todo-form.tsx`).
- Hooks: `camelCase` with a `use` prefix (e.g. `useMediaQuery`), file
  named `use-media-query.ts`.
- Server Actions: verb-first `camelCase` function name (e.g.
  `createTodo`, `deleteTodo`), file `create-todo.ts` — one action per
  file once a feature has more than 2–3.
- Queries: `get`/`list` prefix (e.g. `getTodoById`, `listTodosByUser`),
  file `get-todo-by-id.ts`.
- Zod schemas: `<name>Schema` (e.g. `createTodoSchema`), inferred type
  `<Name>Input`/`<Name>Output` via `z.infer<>`.
- Prisma models: `PascalCase` singular (e.g. `Todo`, `User`) — Prisma
  convention, matches generated client types.
- Errors: subclasses of `AppError` end in `Error` (e.g.
  `NotFoundError`, `ValidationError`).

## Testing

- Unit tests for `features/<feature>/queries` and
  `features/<feature>/actions` — mock the Prisma client (e.g. via
  `vitest-mock-extended` or a test database), never hit a real database
  in unit tests.
- Component tests (React Testing Library) for
  `features/<feature>/components` and `components/ui` — render Server
  Components as async components per RTL's Next.js guidance; Client
  Components render and test interaction normally.
- E2E tests (Playwright) live in `e2e/` at the project root, per the
  web E2E testing rules (`~/.claude/rules/web/testing.md`) — cover
  critical flows only (auth, core CRUD journey), not every page.
- Follow the 80% coverage and AAA test structure from the global testing
  rules.

## Adding a New Feature

1. Add/extend the Prisma model in `prisma/schema.prisma`, run
   `prisma migrate dev`.
2. Define Zod schemas in `features/<feature-name>/schemas/`.
3. Write `queries/` (reads) and `actions/` (writes) against Prisma.
4. Build `components/` — Server Components for display, Client
   Components (`"use client"`) only where interactivity is needed.
5. Wire the feature into a route under `app/`, keeping `page.tsx` thin
   (fetch via `queries/`, render via `components/`).
6. Add tests alongside the feature in `tests/features/<feature-name>/`.

## Common Commands

```bash
# Generate Prisma client after editing schema.prisma
npx prisma generate

# Create + apply a migration in dev
npx prisma migrate dev --name <migration-name>

# Apply committed migrations in production
npx prisma migrate deploy

# Open Prisma Studio to inspect data
npx prisma studio

# Add a shadcn/ui primitive
npx shadcn add <component-name>

# Run unit/component tests
npx vitest

# Run E2E tests
npx playwright test

# Type-check
npx tsc --noEmit
```
