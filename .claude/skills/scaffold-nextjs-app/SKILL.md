# scaffold-nextjs-app

Bootstrap a brand-new Next.js app: brainstorm and confirm an architecture
doc with the user, then generate the codebase (skeleton + one starter
feature) from that confirmed doc.

This skill is for **new** apps / fresh scaffolds, and is **self-contained**:
it bundles its own reference architecture at
`scaffold-nextjs-app/templates/NEXT_ARCHITECTURE.template.md`, plus a
ready-to-copy TypeScript codebase at `scaffold-nextjs-app/templates/next/`
(see "Bundled Next.js Templates" below) — it does not depend on a
`docs/architecture/NEXT_ARCHITECTURE.md` existing anywhere, nor on writing
every file from scratch each run. It is not for adding a feature to an
already-architected app — for that, just follow that project's own
architecture doc directly.

## Bundled Next.js Templates

`scaffold-nextjs-app/templates/next/` mirrors the `src/` tree from the
architecture template, with every file pre-written and working end to end
for a **sign-in** feature (the assumed first feature for these templates),
using a lightweight cookie/JWT session — not a full auth provider. Layout:

```text
templates/next/
├── root/                              # files that belong at the Next.js project root
│   ├── .env.example.tpl
│   ├── middleware.ts.tpl               # Guards /dashboard, redirects to /sign-in
│   └── prisma/
│       ├── schema.prisma.tpl            # User model (email + passwordHash)
│       └── seed.ts.tpl                   # Seeds a demo user (demo@example.com / password123)
└── src/
    ├── app/
    │   ├── (auth)/sign-in/page.tsx.tpl   # Server Component page, renders SignInForm
    │   └── (app)/
    │       ├── layout.tsx.tpl             # Redirects to /sign-in when no session
    │       └── dashboard/page.tsx.tpl      # requireUser() + sign-out form
    ├── features/sign-in/
    │   ├── schemas/sign-in-schema.ts.tpl   # Zod: email + password (min 8)
    │   ├── actions/{sign-in,sign-out}.ts.tpl
    │   ├── queries/get-user-by-email.ts.tpl
    │   ├── components/sign-in-form.tsx.tpl # Client Component, useTransition
    │   └── types.ts.tpl
    └── lib/
        ├── config/env.ts.tpl              # Zod-validated env accessor
        ├── db/prisma.ts.tpl                # Prisma Client singleton
        ├── auth/{session,password}.ts.tpl  # jose JWT cookie session + bcryptjs hashing
        ├── errors/{app-error,format-error}.ts.tpl
        └── utils/cn.ts.tpl                 # clsx + tailwind-merge
```

These are **copy-and-adapt** templates, not blind stamp-outs:

- `.tpl` files use the literal placeholder `{{project_name}}` (currently
  only in `sign-in/page.tsx.tpl`'s heading) — replace it with the confirmed
  project name when copying.
- Strip `.tpl` off every filename on copy (e.g. `session.ts.tpl` →
  `session.ts`); `root/*.tpl` go to the Next.js project root (`root/prisma/`
  → `prisma/`), everything under `src/` keeps its relative path under the
  new project's `src/`.
- Only copy a template file into the new project if the confirmed
  `NEXT_ARCHITECTURE.md` actually calls for that piece (e.g. skip the whole
  `prisma/` tree and `lib/db/prisma.ts` if the user picked a different data
  layer; skip `middleware.ts`/the `(app)` route group if there's no auth yet).
- `components/ui/button.tsx` and `components/ui/input.tsx` are **not**
  bundled — they're generated by the shadcn CLI (`npx shadcn add button
  input`) as part of Step 5, per the architecture doc's `Common Commands`.
  Don't hand-write these; the feature templates import them assuming the
  CLI's default output shape.
- If the user's confirmed architecture differs from a template's
  assumption (different data layer instead of Prisma, different auth
  approach instead of the bundled JWT-cookie session, different feature
  name instead of sign-in), **edit the copied file** to match — the
  template is a starting point, the confirmed architecture doc is the
  source of truth.
- The bundled session implementation (`lib/auth/session.ts.tpl`) is a
  minimal custom JWT-in-httpOnly-cookie scheme via `jose`, chosen so the
  scaffold builds and runs immediately without configuring an OAuth
  provider. If the confirmed architecture picks `next-auth`/Auth.js or a
  third-party provider (Clerk, Supabase Auth, etc.) instead, replace
  `lib/auth/session.ts` and the sign-in action's session call with that
  provider's equivalent as part of Step 5 — do not force-fit the bundled
  session code onto a different auth choice.

## Role & Mindset

Act as an experienced Full-Stack/Next.js developer with deep, hands-on
expertise in the App Router, Server Components, and Server Actions, setting
up a new project for a team. Bring practical, opinionated judgment from
real-world Next.js delivery — data layer, rendering strategy, auth,
performance, and deployment pitfalls — and explain trade-offs in those
terms.

- **Always ask to gather the most information possible, and whenever you hit
  any doubt or ambiguity, stop and ask rather than assuming.** Prefer one
  more clarifying question over a wrong guess. Surface uncertainties
  explicitly and confirm your understanding with the user before acting on
  it.
- Do not guess project name, package manager, or architecture choices — ask.
- Do not generate any code until the user has explicitly confirmed the
  architecture document.
- Keep questions focused, one topic at a time, and summarize understanding
  back to the user before moving to the next step.
- Read the bundled
  `scaffold-nextjs-app/templates/NEXT_ARCHITECTURE.template.md` first — it
  is the **default template** for brainstorming (principles, folder
  structure, layering, data fetching, data layer, configuration,
  auth/middleware, styling, naming, testing, dependencies, commands). Adapt
  it to the user's answers rather than starting from a blank page, unless
  the user wants something materially different. If the current repo also
  happens to have its own `docs/architecture/NEXT_ARCHITECTURE.md`, treat
  the bundled template as authoritative for this skill — don't depend on
  the repo file being present.

## Step 1: Ask Where and What

Ask the user (can be combined into one round of questions):

1. **Target source directory** — default `src/` if not specified. The app
   code will live at `<target_dir>/<project_name>/`.
2. **Project name** — used for the Next.js project directory and as a
   human-readable app name.
3. **Package manager** — `pnpm` (default), `npm`, `yarn`, or `bun`.
4. **Language/style flags for `create-next-app`** — TypeScript (default:
   yes, always), ESLint (default: yes), ESLint config flavor if asked.
5. Confirm the directory doesn't already exist before proceeding; if it
   does, stop and ask the user how to proceed (do not overwrite silently).

## Step 2: Brainstorm the Architecture

Read `scaffold-nextjs-app/templates/NEXT_ARCHITECTURE.template.md`
(bundled with this skill) before asking anything — it is the source of
defaults for every topic below. Work through these with the user to
produce the new project's `NEXT_ARCHITECTURE.md`. For each topic, propose
the bundled template's default and ask the user to confirm or override:

- **Rendering strategy** — App Router + Server Components by default
  (fixed; this skill does not support the Pages Router). Confirm whether
  any route needs to be fully static/ISR vs dynamic.
- **Data layer** — Prisma (default) vs Drizzle vs another ORM; Postgres
  (default) vs another database.
- **Data mutations** — Server Actions (default) for internal mutations,
  Route Handlers reserved for webhooks/external consumers (per the
  reference doc) — confirm this split holds for the project.
- **Client-side data fetching** — none by default (Server Components +
  Server Actions only); confirm whether a screen already known up front
  needs TanStack Query/SWR (e.g. polling, optimistic UI beyond
  `useOptimistic`).
- **Auth** — bundled minimal JWT-cookie session (default, matches the
  templates) vs `next-auth`/Auth.js vs a third-party provider (Clerk,
  Supabase Auth, etc.). If the user wants a real OAuth/social login flow,
  prefer `next-auth` or the provider over extending the bundled session
  code.
- **Styling** — Tailwind CSS + shadcn/ui (default) vs alternatives.
- **Validation** — Zod (default) for Server Action input and `env.ts`.
- **Forms** — `react-hook-form` + Zod resolver (default) vs uncontrolled
  forms with `useActionState`/`useTransition` only (as in the bundled
  sign-in template) — confirm which the project wants as its default form
  pattern.
- **Environment configuration** — Zod-validated `lib/config/env.ts`
  (default), confirm which env vars are known up front.
- **Testing strategy** — **always explicitly confirm with the user**:
  - Which test types to set up now: unit (Vitest), component (React
    Testing Library), E2E (Playwright).
  - Target coverage percentage (repo default is 80% — confirm or
    override).
  - **Do not scaffold `e2e/` or write any tests by default** — only
    generate test setup/files the user explicitly asks for in this step.
    Note this restriction directly in the generated `NEXT_ARCHITECTURE.md`
    Testing section so it's not silently reintroduced later.

Generate `<target_dir>/<project_name>/docs/architecture/NEXT_ARCHITECTURE.md`
(or the path the user prefers) by copying the structure and level of detail
of the bundled `scaffold-nextjs-app/templates/NEXT_ARCHITECTURE.template.md`
— same section set (Principles, Folder Structure, Layering, Data Fetching,
Data Layer, Configuration, Auth & Middleware, Styling, Naming, Testing,
Adding a New Feature, Dependencies to Introduce, Common Commands) — with
every choice replaced by what the user actually confirmed in this step, not
left as the template's defaults.

**Stop here and present the generated file to the user for review.**

## Step 3: Wait for Confirmation

Do not proceed to Step 4 until the user explicitly confirms the
architecture document (e.g. "looks good", "confirmed", "go ahead"). If the
user requests changes, edit the doc and ask again.

## Step 4: Ask About the First Feature

Once the architecture is confirmed, ask the user to describe the first
feature to scaffold (name, purpose, routes, data needs). This is the
feature the generated codebase will demonstrate the architecture with — do
not invent one.

- If the user's first feature **is sign-in** (or close to it), the bundled
  `templates/next/src/features/sign-in/` is a working starting point —
  confirm the field set (email/password vs other identifiers) and whether
  the bundled JWT-cookie session is acceptable before treating Step 5 as
  done; if the user wants `next-auth`/a provider instead, swap that in
  during Step 5 as noted above.
- If the first feature is something **else**, still copy the `lib/` and
  `root/` templates in Step 5 that the architecture calls for (they aren't
  sign-in-specific except for `middleware.ts.tpl`'s protected-route list
  and the `(app)`/`(auth)` route groups), but build the feature folder for
  the user's actual feature from scratch following the architecture doc's
  `Folder Structure` and `Layering` sections — don't force-fit the sign-in
  feature templates onto an unrelated feature.

## Step 5: Generate the Codebase

1. Run `create-next-app` in the target directory with the confirmed
   project name and package manager:
   ```bash
   npx create-next-app@latest <target_dir>/<project_name> \
     --typescript --tailwind --eslint --app --src-dir \
     --import-alias "@/*" --use-<package-manager>
   ```
2. Copy the relevant files from `scaffold-nextjs-app/templates/next/` (see
   "Bundled Next.js Templates" above) into the new project, stripping
   `.tpl` and substituting `{{project_name}}`, instead of writing the
   `lib/`/route-group plumbing from scratch — only skip a template file if
   the confirmed architecture doc doesn't call for that piece. Build out
   any remaining folder/file named in the confirmed `NEXT_ARCHITECTURE.md`
   `Folder Structure` section that isn't covered by a template (e.g. a
   non-sign-in first feature) — do not create folders the architecture doc
   doesn't call for (YAGNI), and do not create test files unless the user
   asked for them in Step 2.
3. Review every copied file against the doc's `Layering`, `Data Fetching`,
   `Data Layer`, `Configuration`, and `Auth & Middleware` sections and
   adjust where the confirmed architecture diverges from the template's
   defaults (e.g. `lib/auth/session.ts`, `middleware.ts`, the feature's
   `queries/`, `actions/`, `components/`).
4. Add the dependencies listed in the doc's `Dependencies to Introduce`
   table — only the ones actually used by the app shell and the first
   feature, not the entire table speculatively:
   ```bash
   <pm> add zod bcryptjs jose @prisma/client
   <pm> add -D prisma
   ```
   (swap `bcryptjs`/`jose` for the user's confirmed auth choice, and
   `@prisma/client`/`prisma` for their confirmed data layer, if different
   from the bundled defaults.)
5. Initialize the data layer if Prisma is in scope: `npx prisma init`
   already ran via `create-next-app`'s absence — instead copy
   `root/prisma/schema.prisma.tpl` → `prisma/schema.prisma` (creating the
   `prisma/` directory), set `DATABASE_URL` in `.env.local` for local dev,
   then run `npx prisma generate` and `npx prisma migrate dev --name init`.
6. Add shadcn/ui and generate the primitives the copied feature components
   import (per `Common Commands`):
   ```bash
   npx shadcn@latest init
   npx shadcn@latest add button input
   ```
7. Copy `root/.env.example.tpl` → `.env.example`, and create a matching
   local `.env.local` for development (never commit `.env.local`).
8. Run the package manager's install, then typecheck and build:
   ```bash
   <pm> install
   npx tsc --noEmit
   <pm> run build
   ```
   Fix any errors before finishing. If a copied template file is edited,
   re-run `tsc --noEmit` to catch regressions.

## Step 6: Generate README

Create `<target_dir>/<project_name>/README.md` summarizing the project per
the confirmed `NEXT_ARCHITECTURE.md`:

- Project name and one-line description (from the user's answers).
- Link to / summary of the architecture doc (principles, folder structure
  at a glance, rendering strategy, data layer, auth, styling).
- How to run/test/build (mirror `CLAUDE.md`-style commands for the new
  project: `<pm> dev`, `<pm> run build`, `npx tsc --noEmit`, `npx prisma
  studio`).
- The first feature that was scaffolded.
- A clear note: **"Generated by AI"** — state plainly that the initial
  codebase and architecture doc were generated by an AI agent (Claude
  Code) from a confirmed architecture document, and should be reviewed
  like any other contribution.

## Step 7: Summary

Print a summary of what was created:

```
| Item                  | Path                                              |
|------------------------|---------------------------------------------------|
| Architecture doc       | <target_dir>/<project_name>/docs/architecture/... |
| Project root           | <target_dir>/<project_name>/                      |
| First feature          | src/features/<feature-name>/                      |
| README                 | <target_dir>/<project_name>/README.md             |
```

Remind the user that no tests were generated unless explicitly requested,
per the confirmed Testing section.

## Notes

- Never run destructive commands (`rm -rf`, overwriting an existing
  project directory) without explicit confirmation.
- The bundled `templates/NEXT_ARCHITECTURE.template.md` is the structural
  reference for every run of this skill, regardless of whether the current
  repo happens to have its own architecture doc. The generated doc is for
  the **new** project and must reflect that project's actual confirmed
  choices, not be a blind copy of the template.
- Never commit real secrets (`SESSION_SECRET`, `DATABASE_URL` with real
  credentials) — only placeholder values in `.env.example`, per the global
  security rules.
- Follow this repo's `git-conventions` skill if the user asks to commit the
  new codebase.
